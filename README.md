# wbmix — управление смесительными узлами на Wiren Board (wb-rules)

Виртуальное устройство для поддержания заданной температуры после смесительного
узла независимо от температуры теплоносителя на входе. Один модуль, две
реализации привода — **фазный (3-точечный)** и **аналоговый 0-10 В**.

Проверено автотестами: 142 проверки, включая отработку возмущений
по входу, отказы датчиков и все защиты.

> **Статус.** Алгоритм и защиты проверены на симуляционном стенде.
> На реальном объекте пусконаладка ещё не проводилась.

## Быстрый старт

```sh
# на контроллере
wget https://github.com/suskirov-commits/wb-mixing-groups/releases/latest/download/wb-mixing-groups_all.deb
dpkg -i wb-mixing-groups_all.deb
```

Дальше: веб-интерфейс → **Настройки** → **«Смесительные узлы (отопление)»**.
Топики датчиков и реле выбираются из выпадающих списков, руками ничего
вписывать не нужно.

Для разработки и доработки — **[PROMPT.md](PROMPT.md)**: полное техническое
задание с описанием алгоритма, ограничений платформы и списком уже
допущенных и исправленных ошибок. Годится и как промт для передачи задачи
другому исполнителю или в другую систему.

## 1. Постановка задачи и почему «просто ПИД» здесь не работает

Котёл даёт 60 °C. В тёплый пол нужно 35 °C, в радиаторы — 50 °C. Трёхходовой
смесительный клапан подмешивает обратку контура в горячий поток. Задача — держать
температуру после узла при том, что температура на входе гуляет: котёл тактует,
работает погодозависимая автоматика источника, включается бойлер ГВС с приоритетом.

Три особенности объекта, из-за которых наивный ПИД даёт либо медленное, либо
колебательное регулирование:

**Транспортное запаздывание.** От движения штока до реакции датчика — 10…30 с
(смеситель + участок трубы). Классическое правило: если запаздывание сопоставимо
с постоянной времени, агрессивный ПИД гарантированно раскачивает контур.

**Переменный коэффициент передачи.** Чувствительность «градус на процент хода»
зависит от разницы (T_вход − T_обратка). При входе 60 °C и обратке 28 °C один
процент хода даёт 0,32 К. Если котёл просел до 42 °C — уже 0,14 К. Настройки,
подобранные на одном режиме, на другом либо вялые, либо неустойчивые.

**Дискретный привод.** У фазного привода нет позиционера: контроллер умеет только
«крутить открытие N секунд». Положение приходится моделировать интегрированием
времени работы, а модель дрейфует.

### Решение: упреждение по модели смешения + ПИ-коррекция

Основную работу делает статическая модель смешения. Для доли открытия `k`:

```
T_смесь = k · T_вход + (1 − k) · T_обратка
   =>  k = (T_уставка − T_обратка) / (T_вход − T_обратка)
```

Это **feed-forward**: как только меняется температура на входе, позиция
пересчитывается сразу, не дожидаясь, пока возмущение доедет до датчика.
Заодно снимается проблема переменного коэффициента передачи — модель уже
содержит эту зависимость в знаменателе.

Поверх работает ПИ-регулятор по фактической температуре: он убирает ошибку
модели — нелинейную характеристику клапана (равнопроцентная вместо линейной),
теплопотери, погрешность оценки обратки.

**Результат на стенде** (вход 60 °C, ступень до 75 °C, затем провал до 42 °C):

| Возмущение | FF + ПИ | Только ПИ |
|---|---|---|
| Скачок входа +15 К | макс **0,64 К**, средн 0,23 К | макс 1,30 К, средн 0,42 К |
| Провал входа −33 К | макс **1,37 К**, средн 0,20 К | макс 3,65 К, средн 1,64 К |
| Установившийся режим | макс **0,35 К** | макс 0,77 К |
| Выход на уставку с холода | 7 мин | 14 мин |

По самому тяжёлому возмущению упреждение даёт выигрыш в 2,7 раза по максимуму и
в 8 раз по средней ошибке.

## 2. Установка

### Способ 1 — .deb из релиза (рекомендуемый)

На контроллере, две строки:

```sh
wget https://github.com/suskirov-commits/wb-mixing-groups/releases/latest/download/wb-mixing-groups_all.deb
dpkg -i wb-mixing-groups_all.deb
```

Обновление — **та же команда**. Один пакет подходит для Wiren Board 6, 7 и 8:
внутри только JavaScript и JSON, архитектура `all`, отдельные сборки под
armhf и arm64 не нужны.

Конфигурация `/etc/wb-mixing-groups.conf` объявлена в `conffiles`, поэтому
при обновлении dpkg **не тронет настройки объекта**. Если эталонный конфиг
в новой версии изменился, dpkg положит его рядом как `.dpkg-dist` и скажет
об этом.

Удаление: `apt remove wb-mixing-groups` (конфигурация останется) или
`apt purge wb-mixing-groups` (вместе с конфигурацией).

Проверить, что стоит на объекте:

```sh
dpkg -l wb-mixing-groups
cat /usr/share/wbmix/VERSION
```

Релизы собираются GitHub Actions по тегу:

```sh
git tag v1.0.0 && git push --tags
```

Пакет не соберётся, пока не пройдут автотесты — регулятор, защиты, приводы,
схема настроек, установщик. Выложить в релиз заведомо битую версию нельзя.

### Способ 2 — git-копия на контроллере

Удобно, когда нужно быстро править код прямо на объекте.

```sh
apt-get update && apt-get install -y git
git clone https://github.com/suskirov-commits/wb-mixing-groups.git /opt/wbmix
/opt/wbmix/install.sh
```

Дальше обновление — одна команда:

```sh
ssh root@<ip> wbmix-update
```

`wbmix-update` кладётся в `/usr/local/bin` при установке: делает `git pull`
и запускает `install.sh` заново.

Что делает `install.sh`:

* проверяет JSON схемы и конфигурации **до** того, как что-либо трогает;
* делает бэкап в `/var/backups/wbmix/` (хранятся последние 10);
* никогда не перезаписывает конфигурацию объекта — при изменении эталона
  кладёт рядом `.conf.new` и говорит, чем сравнить;
* перезапускает `wb-rules` и проверяет, что сервис поднялся; если нет —
  показывает журнал и **откатывает** на предыдущую версию;
* идемпотентен, запускать можно сколько угодно раз.

Удаление: `/opt/wbmix/install.sh --uninstall` (или `--purge` вместе
с конфигурацией).

### Способ 3 — залить с рабочей машины без git на контроллере

```sh
make deploy HOST=192.168.1.50
```

Пакует рабочую копию, кладёт в `/opt/wbmix` по ssh и запускает установщик.

### Способ 4 — один файл через веб-интерфейс

Если ssh недоступен или нужно быстро проверить идею на одном объекте.
Модули и конфигурация вшиты внутрь, ставить больше нечего.

1. Веб-интерфейс → **Правила** → **Новый скрипт**
2. Вставить содержимое `dist/wb-mixing-groups.js`
3. Поправить секцию `CONFIG` в начале файла — топики и параметры
4. Сохранить

Минус: страницы настроек с выпадающими списками здесь нет, топики правятся
руками в тексте скрипта. И на каждом объекте оказывается своя копия кода.

### Что куда ложится

```
/etc/wb-rules-modules/wbmix-*.js                                 модули
/etc/wb-rules/mixing-groups.js                                   точка входа
/etc/wb-mixing-groups.conf                                       конфигурация
/usr/share/wb-mqtt-confed/schemas/wb-mixing-groups.schema.json   форма настроек
/usr/share/wbmix/                                                README, эталон, версия
/usr/local/bin/wbmix-update                                      обновлялка (способ 2)
```

Всё это переживает штатное обновление прошивки контроллера: `/etc`,
`/usr/share` и установленные apt-пакеты при обновлении сохраняются.

### Пересборка однофайловой версии

После правки исходников:

```sh
make build      # -> dist/wb-mixing-groups.js
make test       # все автотесты, включая проверку сборки
```

Узнать реальные имена MQTT-топиков:

```sh
mosquitto_sub -t '/devices/+/controls/+' -v | grep -v meta
```

Требования: wb-rules 2.x (WB6/WB7/WB8). Код на ECMAScript 5 — движок duktape
не понимает `let`, `const`, стрелочные функции и шаблонные строки.

## 3. Страница настроек: топики из выпадающего списка

Схема `wb-mixing-groups.schema.json` описывает форму, которую рисует
`wb-mqtt-confed` — тот же механизм, на котором сделаны штатные сценарии
Wiren Board. Ничего дополнительно устанавливать не нужно, confed уже стоит
в прошивке.

**Настройки → Смесительные узлы (отопление)**

* Кнопка «добавить» создаёт ещё один смесительный узел — сколько угодно
  контуров на одном контроллере, каждый со своим виртуальным устройством.
* Все поля топиков — с автодополнением: начинаете печатать и выбираете из
  реально существующих в системе устройств и контролов. Формат
  `устройство/контрол` проверяется тут же, опечатку не пропустит.
* Тип привода выбирается переключателем: «Фазный (3-точечный), два реле» или
  «Аналоговый 0-10 В». Форма перерисовывается — для фазного показываются реле
  и время хода, для аналогового канал и диапазон напряжения.
* У каждого поля есть подсказка: что это, обязательное ли, какие значения
  типичны.
* Числовые параметры ограничены диапазонами — нельзя случайно поставить
  время хода 0 или предел перегрева 200 °C.
* Интерфейс на русском и английском.

При сохранении confed записывает `/etc/wb-mixing-groups.conf` и перезапускает
`wb-rules`. Комментарии из файла при этом теряются — это нормально, справка
живёт в самой форме.

**Что настраивается уже не здесь, а на странице устройства**, на лету и без
перезапуска: уставка, режим, `Kp`, `Ki`, предел перегрева, наклон и сдвиг
погодозависимой кривой, ручное положение клапана. То есть всё, что реально
крутится при пусконаладке и после неё. В конфигурацию заходят один раз при
монтаже.

Проверить схему до заливки на контроллер:

```bash
node test/schema.js
```

## 4. Подключение оборудования

### 4.1 Фазный (3-точечный) привод

Привод имеет три провода управления: общий (N), «открыть», «закрыть». Питание
230 В или 24 В. Нужны **два релейных выхода** — например, WB-MR6C, WB-MRM2-mini.

```
WB-MR6C  K1 ──── «открыть» (чёрный/L1 привода)
WB-MR6C  K2 ──── «закрыть» (коричневый/L2 привода)
         N  ──── общий привода
WB-MR6C  K3 ──── насос контура
```

Важно:

* Реле **никогда не должны включаться одновременно** — модуль это гарантирует
  программно (`_settle()` перед каждым стартом) и выдерживает паузу на реверс
  (`interlock`, по умолчанию 300 мс). Для приводов без внутренней блокировки
  дополнительно поставьте механическую блокировку контакторов.
* Время полного хода `travelTime` берите **из паспорта привода** и обязательно
  проверьте секундомером на объекте — оно уходит на 10…20 % от паспортного.
* Аварийный термостат защиты тёплого пола (обычно накладной, 55 °C) ставьте
  **в разрыв цепи насоса аппаратно**, а его сухой контакт заводите на вход
  контроллера (`safety.emergencyInput`). Программная защита — второй рубеж,
  а не единственный.
* Дополнительно есть смысл завести НЗ-контакт этого термостата **в разрыв
  цепи реле «открыть»**. Тогда даже при зависшем контроллере кран физически
  нельзя открыть дальше, а закрыть — можно.

#### Настройки модуля реле — обязательно проверить

Привод без возвратной пружины остаётся ровно там, где его бросили. Значит,
единственный способ его остановить — снять команду с реле. Если модуль реле
пропадёт с шины RS-485 в момент хода, а его выходы останутся под управлением
«как было», привод доедет до упора и будет стоять там в распор.

У модулей WB-MR6C v.2 есть таймер безопасного режима: отсчёт идёт от каждого
успешно принятого пакета Modbus, по умолчанию 10 секунд. Настройте в
веб-интерфейсе (Настройки → модуль реле):

| Параметр | Значение | Почему |
|---|---|---|
| Безопасное состояние выходов «открыть» и «закрыть» | **выключено** | при потере связи привод обесточивается |
| Переход в безопасный режим | **включён** | иначе таймер не работает |
| Таймаут безопасного режима | 10 с (по умолчанию) | при ходе 120 с это ≈8 % хода — некритично |
| Состояние при включении питания | **безопасное состояние** | «восстановить предыдущее» здесь опасно: после моргания питания реле включится снова и привод поедет без надзора контроллера |

Обратите внимание: для WB-MAO4 (раздел 4.2) рекомендация **обратная** —
там как раз нужно «восстановить предыдущее состояние», потому что у
аналогового привода 0 В означает команду «закрыть», а не «стой».

Со стороны контроллера потеря связи с модулем реле тоже обрабатывается:
поднимается авария «нет связи с модулем реле», положение клапана помечается
недостоверным, интегратор замораживается. После восстановления связи первый
же такт уходит в калибровку на упор — потому что за время аварии привод мог
сместиться на неизвестную величину.

### 4.2 Аналоговый привод 0-10 В

WB-MAO4 в режиме аналогового выхода, диапазон `0…10000` (мВ).

```
WB-MAO4  Channel 1 ──── вход управления привода (Y)
                   ──── GND / общий
```

Для приводов **2-10 В** задайте `vMin: 2000`. Учтите известную особенность:
привод трактует пропадание сигнала (0 В) как команду «закрыть», а не как
«удерживать положение». Поэтому:

* питайте WB-MAO4 и привод от одного источника;
* в настройках канала MAO4 задайте Power-On State = «установить предыдущее
  состояние», а Safe State — «ничего не делать»;
* иначе при перезагрузке контроллера контур на несколько секунд закроется.

## 5. Конфигурация

Обычно сюда заходить не нужно — всё настраивается на странице из раздела 3.
Раздел описывает, что означает каждый параметр, независимо от того, правите
вы его в форме, в `/etc/wb-mixing-groups.conf` или в секции `CONFIG`
однофайловой сборки. Аннотированный пример на два контура —
`etc/wb-mixing-groups.conf.example`.

### Датчики (`sensors`)

| Поле | Обязателен | Назначение |
|---|---|---|
| `supplyIn` | да | вход узла, от котла. Нужен для упреждения |
| `supplyOut` | да | **выход узла** — по нему регулируем |
| `returnLine` | нет | обратка контура. Сильно повышает точность модели |
| `outdoor` | для кривой | улица |
| `room` | нет | помещение, для коррекции кривой |

Без `returnLine` обратка оценивается как `T_выход − loopDeltaT`. Оценка грубая,
но упреждению достаточно — ошибку доберёт интегратор. Если датчик обратки есть,
поставьте: это самый дешёвый способ улучшить качество.

Датчики обрабатываются не «в лоб»: проверяется `meta/error` (обрыв 1-Wire, потеря
Modbus), физический диапазон, отбраковываются выбросы быстрее 2 К/с, показания
сглаживаются фильтром первого порядка. Авария поднимается только после трёх
подряд плохих чтений — одиночный сбой опроса не роняет контур.

### Привод (`actuator`)

Фазный:

```json
{
  "type": "tristate",
  "open": "wb-mr6c_45/K1",
  "close": "wb-mr6c_45/K2",
  "travelTime": 120,
  "travelTimeClose": 120,
  "minPulse": 500,
  "deadband": 1.5,
  "interlock": 300,
  "recalibrateAfter": 500
}
```

Аналоговый:

```json
{
  "type": "analog",
  "out": "wb-mao4_21/Channel 1",
  "outUnits": "mv",
  "vMin": 0, "vMax": 10000,
  "invert": false,
  "feedback": null
}
```

### Регулирование (`control`)

| Параметр | ТП | Радиаторы | Смысл |
|---|---|---|---|
| `period` | 20 | 5 | такт, с. Для фазного 15…30, для 0-10 В 3…10 |
| `kp` | 3.0 | 2.5 | %/К |
| `ki` | 0.012 | 0.02 | %/(К·с) |
| `kd` | 0 | 0 | оставьте 0 — запаздывание |
| `deadband` | 0.3 | 0.3 | К, зона пониженного усиления |
| `setpointRamp` | 2 | 0 | К/мин, плавный вывод на уставку |
| `loopDeltaT` | 7 | 10 | расчётный перепад контура, К |

### Защиты (`safety`)

* `maxSupply` — **жёсткий предел подачи**. Для тёплого пола 45 °C (выше — риск для
  стяжки и напольного покрытия). При превышении клапан закрывается, насос
  остаётся включённым, чтобы снять тепло. Возврат по гистерезису `maxSupplyHyst`.
* `softLimitBand` — уставка не поднимается выше `maxSupply − softLimitBand`,
  чтобы регулятор не «упирался» в защиту в нормальном режиме.
* `failSafePosition` — положение при отказе датчика подачи. Для ТП — 0.
* `frostProtect` / `frostTemp` — защита от замерзания; работает даже при
  выключенном контуре.
* `emergencyInput` — топик сухого контакта аварийного термостата.
* `deviationAlarm` / `deviationAlarmDelay` — авария «уставка не достигается»:
  сигнализирует засор фильтра, закисший кран, воздух в контуре, отказ насоса.

### Погодозависимая кривая (`curve`)

Расчёт по характеристике отопительного прибора, а не по прямой линии:

```
x     = (T_пом − T_нар) / (T_пом − T_нар.расч)        доля нагрузки
ΔT_ср = ΔT_ср.расч · x^(1/n)                          средний напор
ΔT_к  = ΔT_к.расч · x                                 перепад контура
T_под = T_пом + ΔT_ср + ΔT_к / 2
```

`n` — показатель степени теплоотдачи: **1,1** тёплый пол, **1,3** стальные и
алюминиевые радиаторы, 1,25…1,33 чугун, 1,4 конвекторы. Задайте проектные
`supplyDesign` / `returnDesign` / `outdoorDesign` — дальше кривая строится сама.

Подстройка на объекте делается двумя ручками прямо в веб-интерфейсе:
`curve_slope` (наклон, %) и `curve_shift` (параллельный сдвиг, К).

Правило коррекции: **холодно в морозы, нормально в оттепель → поднять наклон**;
**холодно всегда → поднять сдвиг**; **жарко в оттепель, нормально в мороз →
опустить сдвиг**.

## 6. Виртуальное устройство

После установки в веб-интерфейсе появляется устройство (`mix_floor`, `mix_rad`):

| Контрол | Тип | Назначение |
|---|---|---|
| `enabled` | switch | включение контура |
| `mode` | enum | 0 ручной / 1 фикс. уставка / 2 кривая |
| `setpoint` | range | уставка для режима 1 |
| `target` | temperature | фактическая расчётная уставка (после кривой, рампы и ограничений) |
| `t_in` / `t_mix` / `t_ret` / `t_out` / `t_room` | temperature | показания датчиков |
| `deviation` | value | рассогласование, К |
| `position` | value | положение клапана, % |
| `position_cmd` | range | ручное положение (режим 0) |
| `ff` | value | вклад упреждения, % — по нему видно, работает ли модель |
| `pid_i` | value | интегратор — по нему видно, «догоняет» ли регулятор |
| `state` | text | Выключен / Нагрев / Уставка держится / Нет тепла на входе / Ограничение по перегреву / Авария / Калибровка / Лето |

Все контролы доступны по MQTT: `/devices/mix_floor/controls/setpoint/on` и т. д. —
интегрируется с Home Assistant, панелями, сценариями.

## 7. Как решена проблема положения фазного привода

У 3-точечного привода нет обратной связи, поэтому положение — это модель.
Что сделано, чтобы модель не разъезжалась с реальностью:

1. **Интегрирование фактического времени работы.** Позиция обновляется по
   реально прошедшему времени между включением и выключением реле, а не по
   заказанной длительности. Прерывание импульса (авария, выключение) учитывается
   корректно.

2. **Прижим к упорам.** Команда «полностью закрыть» выполняется прогоном
   на 120 % времени хода, после чего позиция принудительно приравнивается нулю,
   а накопленная ошибка обнуляется. То же для полного открытия.

3. **Плановая рекалибровка.** После `recalibrateAfter` процентов суммарного хода
   (по умолчанию 500 %) выполняется прогон на ближайший упор.

4. **Недоверие после рестарта.** Сохранённая в PersistentStorage позиция
   восстанавливается для отображения, но помечается как недостоверная: во время
   простоя контроллера кран могли крутить вручную. Первый же такт после
   перезапуска уходит в калибровку.

5. **Контроль связи с модулем реле.** Каждый такт проверяется `meta/error`
   обоих релейных топиков. Пропала связь — авария, положение недостоверно,
   интегратор заморожен; вернулась — калибровка. Для привода без пружины это
   не формальность: пока связи нет, кран стоит в неизвестном месте и сам
   никуда не вернётся.

6. **Заморозка интегратора на время калибровки.** Пока идёт прогон на упор,
   привод не может отработать команду. Если этого не учесть, за две минуты
   интегратор набирает полный ход и после калибровки клапан уходит на упор —
   в симуляции это давало заброс до 47 °C в контуре тёплого пола.

7. **Зона нечувствительности не меньше минимального импульса.** Если запросить
   перемещение короче `minPulse`, привод не тронется — реле щёлкнет впустую.
   Модуль автоматически поднимает `deadband` до эквивалента `minPulse` и
   **не обновляет** позицию, когда движение не выполнено. За счёт этого мелкие
   приращения накапливаются и отрабатываются одним нормальным импульсом.
   На стенде: 80 включений реле за 2,5 часа при точности 0,35 К.

8. **Ограничение импульса тактом.** Длительность импульса не превышает 85 % такта,
   чтобы движение всегда завершалось до следующего расчёта. Большие перемещения
   набираются за несколько тактов.

## 8. Пусконаладка

**Шаг 1. Проверка каналов.** Режим `mode = 0` (ручной). Задайте `position_cmd = 100`,
убедитесь, что кран открывается в сторону котла (`t_mix` растёт к `t_in`).
Если наоборот — поменяйте реле местами или задайте `"invert": true`.

**Шаг 2. Замер времени хода.** Из положения 0 подайте 100 % и засеките
секундомером время до срабатывания концевика (щелчок / изменение звука).
Впишите в `travelTime`. Повторите для закрытия — если отличается больше чем на
10 %, задайте `travelTimeClose` отдельно.

**Шаг 3. Проверка защит.** Временно опустите `max_supply` до значения ниже текущей
`t_mix` — контур должен уйти в «Ограничение по перегреву» и закрыть клапан.
Отключите датчик подачи — должна появиться авария и клапан закрыться. Верните.

**Шаг 4. Настройка ПИ.** Начните с `kp` из таблицы, `ki = 0`. Ступенькой измените
уставку на 5 К и посмотрите на график `t_mix`:

* вялый выход, «недоезд» — поднимайте `kp` на 30 %;
* колебания с периодом в несколько минут — снижайте `kp` вдвое;
* добившись 1–2 затухающих полуволн, поднимайте `ki` от 0,005 с шагом ×1,5,
  пока статическая ошибка не уйдёт за 10–15 минут. Дальше не увеличивайте:
  интегратор начнёт раскачивать контур.

`kd` для смесительных узлов оставляйте нулевым.

**Шаг 5. Контроль износа привода.** Через сутки посмотрите в логе число включений.
Ориентир — не больше 2–3 в минуту в установившемся режиме. Если больше,
увеличьте `deadband` привода до 2–3 % или такт `period` до 30 с. Ресурс типового
привода — порядка миллиона переключений; 3 в минуту это ~6 лет непрерывной работы.

**Шаг 6. Кривая.** Переведите `mode = 2`, наблюдайте неделю, корректируйте
`curve_slope` / `curve_shift` по правилу из раздела 4.

## 9. Что ещё стоит учесть на объекте

**Насосы.** Модуль включает насос контура, держит выбег 5 минут после остановки
и раз в неделю прогоняет насос и клапан от закисания. Если насос управляется
самим смесительным узлом или котлом — оставьте `pump.topic = null`.

**Запрос тепла источнику.** Если котёл управляется сухим контактом или через
модуль OpenTherm, задайте `demand.topic` — контур будет запрашивать тепло только
когда оно нужно. Когда контуров несколько, запросы объединяются по «или» на
стороне котла (отдельное правило, здесь не входит).

**Приоритет ГВС.** Во время нагрева бойлера котёл уходит на 75–80 °C.
Упреждение это отработает автоматически, но если бойлер перекрывает подачу в
отопление, имеет смысл на это время выключать контуры отдельным правилом.

**Гидравлика.** Регулятор не спасёт от неправильно подобранного Kvs клапана.
Если при уставке 35 °C клапан работает в диапазоне 5…15 % — клапан велик,
регулирование будет дёрганым. Нормальный рабочий диапазон — 25…75 %.
Контрол `position` за неделю показывает это наглядно.

**Балансировка.** Расчётный перепад контура (`loopDeltaT`) должен соответствовать
реальности. Если фактический перепад 3 К вместо 7 — насос гонит слишком быстро,
и оценка обратки будет врать (при отсутствии датчика обратки).

## 10. Архитектура кода

Четыре модуля, каждый со своей зоной ответственности. Разделение не
косметическое: алгоритм регулирования, работа с железом и логика узла
меняются по разным причинам и тестируются отдельно.

```
wbmix-util.js       Sensor  — чтение датчика с проверкой meta/error,
                              физического диапазона, отбраковкой выбросов
                              и фильтром первого порядка
                    Ema     — фильтр
                    clamp, round, def — хелперы

wbmix-pid.js        Pid     — ПИ(Д), рассчитанный на работу ПОВЕРХ
                              упреждения: anti-windup back-calculation
                              учитывает вклад FF, есть безударный сброс

wbmix-actuator.js   create(cfg) -> TristateActuator | AnalogActuator
                    Единый интерфейс:
                      apply(target, budgetMs) -> "idle"|"open"|"close"|
                                                 "calibrate"|"busy"|
                                                 "link_fault"|"set"
                      getPosition(), isPositionTrusted(), isBusy()
                      halt(), calibrate(dir, cb), getFault(), stats()

wbmix-group.js      MixingGroup — виртуальное устройство, тактовый цикл,
                                  расчёт уставки, кривая, защиты, насос
                    create(cfg) — фабрика с реестром в module.static
```

Добавить третий тип привода (шаговый, Modbus-позиционер) — это новый класс
в `wbmix-actuator.js` с тем же интерфейсом и ветка в `create()`. Логику
узла трогать не нужно.

Тактовый цикл `MixingGroup._tick()` идёт строго по приоритетам:

```
опрос датчиков
  -> защита от замерзания        (выше выключателя)
  -> внешний аварийный термостат
  -> выключен / лето
  -> отказ датчика выхода        (безопасное положение)
  -> ручной режим                (предел перегрева всё равно работает)
  -> расчёт уставки              (фикс. / кривая -> мягкий предел -> рампа)
  -> жёсткий предел перегрева
  -> упреждение по модели смешения
  -> ПИ-коррекция -> привод
  -> состояние, аварии, запрос тепла, антизалипание
```

Порядок важен: каждая следующая ступень выполняется, только если
предыдущая не перехватила управление.

Правила работы с кодом:

* перед коммитом — `make test`, все 142 проверки должны проходить;
* после правки модулей — `make build`, иначе CI упадёт на проверке
  соответствия `dist/` исходникам; `dist/wb-mixing-groups.js` руками
  не редактировать;
* только ECMAScript 5: `npx acorn --ecma5 --silent <файл>`;
* новая защита — с тестом на срабатывание **и** на снятие;
* всё, что настраивается после пусконаладки, должно быть контролом
  виртуального устройства, а не полем конфигурации.

## 12. Точки расширения

* **Каскад по температуре помещения.** Наружный контур ПИ по `t_room` задаёт
  уставку подачи вместо кривой. Каркас уже есть: `roomGain` делает пропорциональную
  коррекцию, полноценный каскад — это второй экземпляр `Pid` в `_curveSetpoint`.
* **Защита обратки котла** (твердотопливный, конденсационный): ограничение
  позиции по минимальной температуре обратки на котёл.
* **Ограничение мощности контура** по перепаду `t_mix − t_ret`.
* **Сушка стяжки**: программа с суточным профилем уставки. Механизм рампы
  (`setpointRamp`) и уже реализованное ограничение уставки — готовая основа.
